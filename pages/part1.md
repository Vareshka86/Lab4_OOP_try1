Вариант 5 — «Устройства умного дома». Версия v0.1: каркас иерархии SmartDevice → PoweredDevice →

## Условие задания

**Общие требования ко всем вариантам:**

- иерархия минимум из 3 уровней наследования (абстрактный базовый → промежуточный → конкретный класс);
- базовый класс абстрактный и содержит хотя бы одну чисто виртуальную функцию;
- хотя бы одна виртуальная функция с реализацией по умолчанию в базовом или промежуточном классе и её
  переопределение в наследниках;
- корректные конструктор копирования и оператор присваивания (с глубоким копированием при наличии
  динамических ресурсов);
- хотя бы одна статическая функция и один статический член-данные с осмысленной ролью;
- корректная работа с полиморфизмом через указатели и ссылки на базовый класс;
- при необходимости — множественное наследование;
- отдельный файл с тестами: создание объектов всех типов, полиморфный вызов, работа статических членов,
  копирование и присваивание (независимость копий), обработка исключений, множественное наследование;
- git — не менее 7 осмысленных коммитов; документация Doxygen; UML-диаграмма классов в PlantUML.

**Вариант 5. Устройства умного дома.** Иерархия: от абстрактного SmartDevice через PoweredDevice к
LightBulb, Thermostat, а также составное устройство SmartOutlet (розетка + датчик).

- SmartDevice — абстрактный, с `turnOn()`, `turnOff()`, `getStatus()` (чисто виртуальные).
- PoweredDevice — добавляет `powerConsumption` и виртуальную `getPowerUsage()`.
- Конкретные LightBulb (яркость, цвет) и Thermostat (температура, режим).
- SmartOutlet наследуется от PoweredDevice и от интерфейса ISensor (с `getCurrentVoltage()`) —
  множественное наследование.
- Статический член: общий потреблённый кВт·ч всеми устройствами (накапливается при включении и выключении).
- Статическая функция `getTotalEnergyConsumed()`.
- Конструктор копирования и присваивание — с учётом состояния (вкл/выкл) и параметров.
- В тестах — создать массив устройств, включить и выключить их, проверить статистику.

## Абстрактные классы и чисто виртуальные функции

```cpp
class SmartDevice {
public:
    virtual bool turnOn() = 0;               // = 0 - чисто виртуальная: реализации нет
    virtual bool turnOff() = 0;
    virtual std::string getStatus() const = 0;
    virtual ~SmartDevice();                  // виртуальный деструктор
    ...
};
```

Класс с хотя бы одной чисто виртуальной функцией — **абстрактный**: создать его объект нельзя, он
задаёт только «что умеет любое устройство». PoweredDevice реализует `turnOn()` и `turnOff()`, но
`getStatus()` у него по-прежнему чисто виртуальная, поэтому он тоже абстрактный. LightBulb реализует
всё — это конкретный класс, его объекты создаются.

Конструкторы SmartDevice и PoweredDevice объявлены `protected`: их вызывают только конструкторы
наследников.

## Виртуальная функция с реализацией по умолчанию

```cpp
// PoweredDevice - реализация по умолчанию
virtual double getPowerUsage() const { return isOn() ? powerConsumption_ : 0.0; }

// LightBulb - переопределение
double getPowerUsage() const override { return isOn() ? getPowerConsumption() * brightness_ / 100.0 : 0.0; }
```

Вызов через указатель или ссылку на базовый класс выбирает версию по **настоящему** типу объекта:
для лампы на 60 Вт с яркостью 50 % `powered.getPowerUsage()` даёт 30 Вт, хотя `powered` — ссылка на
PoweredDevice. Явный вызов `powered.PoweredDevice::getPowerUsage()` даёт реализацию по умолчанию —
60 Вт; тест 2 проверяет обе.

Слово `override` просит компилятор проверить, что функция действительно переопределяет виртуальную
функцию базового класса: опечатка в имени или параметрах станет ошибкой компиляции.

## Учёт энергии и статические члены

Время в программе модельное: статическое поле `clockHours_` сдвигает статический метод
`PoweredDevice::advanceClock(часы)`. Так результаты тестов не зависят от настоящих часов и всегда
одинаковые.

1. `turnOn()` запоминает модельный час включения.
2. Пока устройство включено, оно тратит `getPowerUsage()` ватт.
3. `turnOff()` засчитывает энергию: кВт·ч = Вт × часы / 1000 — устройству и общему статическому
   счётчику `totalEnergyKWh_`.
4. Если у включённой лампы меняется яркость, `setBrightness()` сначала вызывает `updateMeter()`:
   энергия до изменения засчитывается по старой мощности, после — по новой.

`getTotalEnergyConsumed()` — статическая функция: общий счётчик один на все устройства, и вызывается
она через имя класса, без объекта. Статические поля объявлены в классе, а определены в .cpp
(`double PoweredDevice::totalEnergyKWh_ = 0.0;`) — в C++14 иначе нельзя.

## Виртуальный деструктор и выключение при уничтожении

```cpp
SmartDevice* device = new LightBulb("Ванная", 60.0, 100, "белый");
delete device;   // вызываются ~LightBulb, ~PoweredDevice, ~SmartDevice
```

Деструктор SmartDevice виртуальный, поэтому `delete` через указатель на базовый класс вызывает
деструкторы всех уровней, начиная с LightBulb. Без `virtual` вызвался бы только ~SmartDevice — это
неопределённое поведение.

Деструктор LightBulb выключает включённую лампу, чтобы энергия последнего интервала попала в
статистику. Внутри `turnOff()` вызывается виртуальная `getPowerUsage()`; в теле ~LightBulb объект ещё
является лампой, и вызывается версия лампы. В деструкторе PoweredDevice так сделать нельзя: часть
«лампа» к тому моменту уже уничтожена, и вызвалась бы реализация по умолчанию с неверной мощностью.

## Копирование до части 4

Конструктор копирования и присваивание в SmartDevice пока объявлены `= delete`. Копирование
«по умолчанию» скопировало бы и час начала учёта, и энергия включённого устройства засчиталась бы
дважды — у оригинала и у копии. Правильное копирование с учётом состояния — в части 4 (v1.0).

## Защита от ошибок

| Ошибка | Реакция |
|--------|---------|
| пустое имя устройства | `std::invalid_argument`, объект не создаётся |
| мощность 0 и меньше, не число | `std::invalid_argument` |
| яркость вне 1–100 %, пустой цвет | `std::invalid_argument`; `setBrightness()` и `setColor()` не меняют лампу |
| `advanceClock()` на 0 часов, назад или на «не число» | `std::invalid_argument`, время прежнее |

Если исключение брошено в конструкторе LightBulb, уже построенные части PoweredDevice и SmartDevice
уничтожаются их деструкторами, поэтому счётчик устройств остаётся верным — тест 4 это проверяет.

**Проверка.** Тесты программы — 27 проверок из 27. Отдельная тестовая программа — 16 проверок из 16:
свойства типов (SmartDevice и PoweredDevice абстрактные, LightBulb — нет, деструктор виртуальный,
копирование запрещено), дробные интервалы времени, смена яркости у выключенной лампы, многократная
смена яркости, энергия при уничтожении включённой лампы, удаление через указатель на PoweredDevice,
исключение в конструкторе.
